# OptiRoute — Capability Matrix Specification

## Overview

The capability matrix is a JSON file at `data/capability_matrix.json` that describes the strengths, weaknesses, and costs of each model — both Fireworks API models and local models. It is the **heart** of OptiRoute's routing decisions.

## Schema

```json
{
  "<model-id>": {
    "capabilities": {
      "math": <float 0-1>,
      "reasoning": <float 0-1>,
      "code": <float 0-1>,
      "creative": <float 0-1>,
      "translation": <float 0-1>,
      "extraction": <float 0-1>,
      "retrieval": <float 0-1>,
      "general_qa": <float 0-1>
    },
    "cost_per_1k_input": <float>,
    "cost_per_1k_output": <float>,
    "avg_output_multiplier": <float>,
    "max_context": <int>,
    "fails_on": [<string>, ...],
    "avg_latency_ms": <float>,
    "is_local": <bool>
  }
}
```

### Field Definitions

| Field | Type | Description |
|---|---|---|
| `capabilities` | `dict[str, float]` | Per-dimension accuracy scores (0=useless, 1=perfect). Generated by offline benchmark. |
| `cost_per_1k_input` | `float` | USD cost per 1,000 input tokens. **$0.00 for local models.** |
| `cost_per_1k_output` | `float` | USD cost per 1,000 output tokens. **$0.00 for local models.** |
| `avg_output_multiplier` | `float` | Multiplier on output tokens to account for overhead (e.g., Kimi's thinking tokens = 1.3) |
| `max_context` | `int` | Maximum context window in tokens |
| `fails_on` | `list[str]` | Task categories where the model scores < 0.5 in benchmarks. Used for hard exclusion. |
| `avg_latency_ms` | `float` | Average response latency in milliseconds (measured during benchmarks) |
| `is_local` | `bool` | **NEW**: `true` for local models, `false` or absent for Fireworks API models. Used by the pipeline to dispatch to the correct executor. |

### Capability Dimensions

| Dimension | What it measures |
|---|---|
| `math` | Arithmetic, algebra, word problems, numerical reasoning |
| `reasoning` | Logical deduction, multi-step analysis, comparisons |
| `code` | Code generation, debugging, algorithms, syntax |
| `creative` | Story writing, poetry, creative text generation |
| `translation` | Language-to-language translation |
| `extraction` | Extracting structured info from unstructured text |
| `retrieval` | Knowledge recall, factual QA |
| `general_qa` | General question answering, instruction following |

## Local Model Entry

Local models are entries with `cost_per_1k_input = 0.0` and `cost_per_1k_output = 0.0`. The decision engine's "pick cheapest meeting accuracy threshold" algorithm will **automatically prefer** the local model whenever its weighted accuracy meets the required threshold — no special-casing needed.

```json
"local:qwen-2.5-3b": {
    "capabilities": {
        "math": 0.55,
        "reasoning": 0.50,
        "code": 0.45,
        "creative": 0.65,
        "translation": 0.60,
        "extraction": 0.60,
        "retrieval": 0.70,
        "general_qa": 0.72
    },
    "cost_per_1k_input": 0.0,
    "cost_per_1k_output": 0.0,
    "avg_output_multiplier": 1.0,
    "max_context": 2048,
    "fails_on": ["code", "math"],
    "avg_latency_ms": 3000,
    "is_local": true
}
```

> **Important**: These capability scores must be generated from **offline benchmarking only**. Never benchmark models inside the evaluation container.

### Context Length Constraint

The local model's `max_context` (typically 2048 tokens) is much smaller than Fireworks models (256K+). The pipeline performs a **pre-check** before dispatching to the local model:
- If the estimated input tokens exceed 90% of `max_context`, skip the local model entirely
- This prevents wasting latency on a model that will almost certainly truncate or fail

## How It's Generated

### Default (Day 0)
Pre-populated with reasonable estimates:
- **Fireworks models**: Based on model research and architecture analysis
- **Local model**: Conservative estimates (intentionally low) until benchmarked

### After Offline Benchmarks
The benchmark engine (`app/benchmark/`) runs curated datasets through all models (including the local model), evaluates accuracy per category, and overwrites `capability_matrix.json` with measured scores.

### Failure Patterns
If a model scores < 0.5 on any category during benchmarks, that category is added to `fails_on`. The decision engine will **never** route that task type to that model, preventing expensive retries.

## Usage in Routing

```python
# Weighted average scoring (full task vector, not just dominant task type)
predicted_accuracy = (
    sum(task_vector[d] * model.capabilities[d] for d in dimensions)
    / sum(task_vector[d] for d in dimensions)
)

# Cost estimation (local model = $0.00)
estimated_cost = (
    input_tokens * model.cost_per_1k_input / 1000
    + output_tokens * model.avg_output_multiplier * model.cost_per_1k_output / 1000
)
```
