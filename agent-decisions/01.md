# Agent Decisions — `spec/01.md`

Corresponds to: [`spec/01.md`](../spec/01.md)

This document records every significant decision made while implementing the solution described in `spec/01.md`.

---

## Problem Understanding

`spec/01.md` asked us to replace the existing regex/heuristic routing layer with a **local LLM router** — a small local model that:
- Decides which backend to use per request (local, kimi, minimax)
- Executes low-effort tasks itself (saving all Fireworks tokens)
- Runs entirely inside the Docker container with no external runtime

The scoring metric is: **accuracy gate first, then fewest Fireworks tokens wins**.

---

## Decision 1 — Execution Model: Batch CLI, not HTTP Server

**What spec said**: Tasks come in via files; output must be written to a file.

**What the original codebase had**: A FastAPI HTTP server (`uvicorn main:app`) as the Docker `CMD`. This would run forever and never produce `/output/results.json`.

**Decision**: Create `agent.py` — a separate async batch script that:
- Reads `/input/tasks.json` on startup
- Processes every task sequentially via `RoutingPipeline.route()`
- Writes `[{task_id, answer}, ...]` to `/output/results.json`
- Exits with code `0` on success

`main.py` and the FastAPI server are kept untouched for local dev/testing via `curl`. Only the Dockerfile `CMD` was changed to point to `agent.py`.

---

## Decision 2 — Local Model Runtime: `llama-cpp-python` (not Ollama)

**What spec said**: "A local model which is light (1-6B parameters)... local model's token count counts as zero."

**Official clarification (Discord)**: "No Ollama or model runtime is pre-installed: bundle model weights directly in your Docker image."

**Decision**: Use `llama-cpp-python` with a bundled GGUF file.
- `llama-cpp-python` installs as a pure Python package — no separate server, no HTTP overhead
- Pre-built CPU wheels exist at `https://abetlen.github.io/llama-cpp-python/whl/cpu` — no build tools needed at install time
- Model weights are downloaded during `docker build` (Stage 2) and baked into the image
- Inference at runtime is fully offline — no internet required

---

## Decision 3 — Local Model Choice: Qwen2.5-3B-Instruct Q4_K_M

**What spec said**: Available local models include `qwen2.5:1.5b-instruct` (986 MB), `gemma2:2b` (1.6 GB), `phi3:mini` (2.2 GB). Use models in the 1–6B range.

**Official clarification (Discord)**: "2B–3B 4-bit quantized models fit comfortably; a 7B 4-bit fills the full RAM budget."

**Decision**: Use **Qwen2.5-3B-Instruct Q4_K_M** (~1.9 GB GGUF, ~2.3 GB RAM).

| Model | GGUF Size | Est. RAM | Why rejected |
|---|---|---|---|
| qwen2.5-1.5b Q4_K_M | 986 MB | ~1.2 GB | Good fit, but lower accuracy → more Fireworks escalations |
| **qwen2.5-3b Q4_K_M** ✅ | 1.9 GB | ~2.3 GB | Best accuracy/RAM tradeoff in the safe zone |
| phi3:mini Q4_K_M | 2.2 GB | ~2.7 GB | Fits, but leaves less headroom for agent code |
| gemma2:2b Q4_K_M | 1.6 GB | ~2.0 GB | Qwen2.5 has better instruction following for NER/sentiment |

Rationale: Every task the 3B model answers correctly instead of escalating to Fireworks = $0 cost + better rank. The accuracy gain over 1.5B on NER, summarisation, and sentiment is worth the extra 1 GB.

---

## Decision 4 — One Model Instance for Both Routing and Execution

**Problem**: If we load a separate "router model" and a separate "executor model", RAM doubles.

**Decision**: The same Qwen2.5-3B instance serves as both:
- **Router**: `route(prompt)` → `max_tokens=15`, `temperature=0.0` → outputs exactly one of `local`, `minimax-m3`, or `kimi-k2p7-code`
- **Executor**: `execute(prompt, task_type)` → normal inference with task-appropriate settings

The routing call is very cheap (15 tokens in, 1 token out, ~100ms). The model is loaded once at pipeline startup and reused for every task.

---

## Decision 5 — Routing Decision Chain (4 Levels)

The pipeline resolves model selection in priority order:

```
1. force_model override          — testing/debugging only
2. Deterministic bypass          — pure math/JSON → calculator/parser tool ($0, instant)
3. Local LLM router              — Qwen2.5-3B, max_tokens=15, temp=0.0
4. Heuristic decision engine     — regex/keyword fallback (original code, always works)
```

**Why keep the heuristic engine?** It's the original codebase's router. If the GGUF file is absent (e.g., CI without the model), the system falls back gracefully without crashing. The heuristic engine acts as a safety net.

---

## Decision 6 — Fireworks Model Lineup (Gemma Models Removed)

**What spec said**: Gemma models (`gemma-4-31b-it`, `gemma-4-26b-a4b-it`, `gemma-4-31b-it-nvfp4`) are listed but "as of now no gemma models are working."

**Decision**: Remove all gemma models from `data/capability_matrix.json` and from `config.py`'s default fallback list. Active Fireworks models:
- **`minimax-m3`** — general reasoning, complex math, fallback for everything
- **`kimi-k2p7-code`** — code tasks only (debug + generation); ~1.3× output token overhead due to mandatory thinking mode

`ALLOWED_MODELS` is parsed from the harness env var at runtime (not hardcoded), so if the harness injects gemma models on evaluation day, they'll automatically be included.

---

## Decision 7 — `ALLOWED_MODELS` Must Be Read from Env at Runtime

**What the original code had**: `allowed_models` hardcoded as a `dict` constant in `config.py`.

**What the spec says**: "The harness injects `ALLOWED_MODELS` at runtime. Do not hardcode model IDs."

**Decision**: `config.py` now reads `ALLOWED_MODELS` from the env as a comma-separated list of full model paths (e.g., `accounts/fireworks/models/minimax-m3`) and parses them into `{short_name: full_path}`. Falls back to `{minimax-m3, kimi-k2p7-code}` when the env var is absent (local dev).

---

## Decision 8 — Routing Few-Shot Prompt Aligned to the 8 Real Eval Categories

**What the original code had**: Internal capability dimensions (`math`, `reasoning`, `code`, `creative`, `translation`, `extraction`, `retrieval`, `general_qa`).

**What the spec actually evaluates**:
1. Factual knowledge
2. Mathematical reasoning
3. Sentiment classification
4. Text summarisation
5. Named entity recognition (NER)
6. Code debugging
7. Logical/deductive reasoning
8. Code generation

**Decision**: The routing prompt's few-shot examples are written against these 8 exact categories. The mapping:
- Categories 1, 3, 4, 5 → `local` (factual, sentiment, NER, summarisation — Qwen 3B handles well)
- Categories 6, 8 → `kimi-k2p7-code` (code debug + code gen)
- Categories 2, 7 → `local` for simple instances, `minimax-m3` for complex multi-step

---

## Decision 9 — `required_accuracy` Threshold Set to 0.75

**What the original code had**: `default_accuracy_threshold = 0.8` in config.

**Why changed**: Qwen2.5-3B's average capability score across extraction/retrieval/general_qa tasks is ~0.72–0.76. With a threshold of 0.80, the heuristic engine would always filter it out — forcing Fireworks calls even for tasks the local model can handle.

**Decision**: Set `required_accuracy = 0.75` in `agent.py` and update `default_accuracy_threshold` in `config.py` to `0.75`. This allows the local model to win routing decisions for its strong categories while still requiring a 75% accuracy floor.

---

## Decision 10 — Context Length Pre-Check Before Local Execution

**Problem**: The local model has a 4096-token context limit. Very long prompts (e.g., text summarisation of a 2000-word article) would silently truncate or error.

**Decision**: Before calling `local.execute()`, the pipeline checks:
```python
if est_tokens > max_ctx * 0.9:
    # Skip local — fall through to Fireworks
```
If the estimated input tokens exceed 90% of the context window, the request is routed directly to Fireworks instead of attempting local execution.

---

## Decision 11 — Escalation on Low Local Confidence

**Decision**: After local execution, the response goes through `ConfidenceValidator`. If `confidence < threshold (0.7)`:
- The local result is saved as `best_result`
- `current_model` is set to `minimax-m3`
- The Fireworks execution loop runs once
- If the Fireworks response is better confidence, it replaces the local result

Max escalation depth remains 2 (original config) to prevent runaway token cost.

---

## Decision 12 — Docker: Multi-Stage Build

Three stages:
1. **`builder`** — installs Python deps including `llama-cpp-python` (needs `gcc`/`cmake`). Build tools are NOT in the final image.
2. **`model-downloader`** — downloads `Qwen2.5-3B-Instruct-Q4_K_M.gguf` (~1.9 GB) from HuggingFace Hub. Separate stage so model is cached by Docker layer independently from code changes.
3. **`final`** — copies `.venv` from builder, `/models` from downloader, app source code. No build tools, no HuggingFace cache — lean final image.

Platform note: build with `--platform linux/amd64` (required by judging VM).

## Summary Table

| Decision | Chosen Approach | Key Reason |
|---|---|---|
| Execution model | Batch CLI `agent.py` | Harness mounts files, not HTTP |
| Local runtime | `llama-cpp-python` + GGUF | No Ollama pre-installed; self-contained |
| Local model | Qwen2.5-3B Q4_K_M | Best accuracy within 4 GB RAM limit |
| Model instance | Single for routing + execution | RAM efficiency |
| Routing chain | 4-level (det → local LLM → heuristic) | Graceful degradation |
| Gemma models | Removed | Not working on Fireworks |
| `ALLOWED_MODELS` | Parse from env at runtime | Harness requirement |
| Few-shot examples | Aligned to 8 real eval categories | Accuracy on actual test prompts |
| Accuracy threshold | 0.75 (was 0.80) | Lets local model win its strong categories |
| Context pre-check | Skip local if tokens > 90% ctx | Prevent truncation errors |
| Escalation | Local → minimax-m3 on low confidence | Safety net for edge cases |
| Docker | Multi-stage build | Clean final image, no build tools |
